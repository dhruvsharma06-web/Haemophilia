# On-device exercise assessment

The `codex/lower-body-source-integration` branch assesses live exercise camera frames on Android. The camera provides YUV frames to `LocalPoseBridge`, which uses the bundled ML Kit pose detector to find 33 joints. The upper-body `ExerciseRulesAssessment` and lower-body source-rules adapter check joint angles, movement stages, posture, return to the start, and repetition timing. The Flutter screen draws the wireframe and feedback. Normal live frames are not uploaded to the Python backend. An assigned session saves completed repetition data and selected error review images to the existing Firebase history; an unassigned practice session does not save history.

This uses a pretrained general pose detector for joint locations. The six lower-body configurations and form checks come from `codex/lower-body-integration`. That branch's three Random Forest bundles are present in this repository as research artifacts; its own code never lets their predictions determine rep form or score. The model card reports one participant, zero cross-validation F1 for the mini-squat and seated-extension labels, and leakage affecting a straight-leg-raise label. The phone does not run those classifiers. Other app features may still use Firebase or the backend.

## Current tracking presets

The app displays these values before and during an exercise. `Start` and `target` are observed camera angles, in degrees. `ROM` is the minimum excursion for an accepted repetition. A repetition also requires a return to the starting range, stable tracking, and no sustained posture error.

| Exercise | Start | Target | Minimum ROM | Return to own start | Camera view |
| --- | ---: | ---: | ---: | ---: | --- |
| Assisted shoulder flexion | both shoulders ≤40° | both shoulders ≥150° | 75° | within 10° | Front |
| Shoulder rotation | within 8° of observed start | both forearms move ≥20° | 15° | within 4° | Front |
| Assisted elbow flexion | active elbow ≥150° | active elbow ≤90° | 50° | within 8° | Front |
| Elbow flexion and extension | both elbows ≥155° | both elbows ≤75° | 70° | within 8° | Front oblique |
| Heel slide | knee ≥170° | knee ≤90° | 15° | within 10° | Side |
| Mini squat | knee ≥165° | knee ≤130° | 15° | within 8° | Side |
| Seated knee extension | knee ≤95° | knee ≥160° | 15° | within 10° | Side |
| Straight leg raise | hip ≥172° | hip ≤140° | 15° | within 10° | Side |
| Terminal knee extension | knee ≤145° | knee ≥170° | 15° | within 6° | Side |
| Squat | knee ≥155° | knee ≤120° | 15° | within 10° | Side |

The upper-body rules are `OnDeviceRules_v3`; lower-body targets and checks are adapted from the original branch. The source squat entry threshold of 105° occurs after its 120° target, so the app uses a 145° entry threshold and retains the 155° return and 120° target. See [exercise references and angle conversion](exercise-rule-references.md) for NHS/WFH sources and the distinction between sourced exercise goals and software scoring tolerances. Tutorials show the animation first and a small angle summary below it. The ordinary elbow demo is a forward curl with fixed upper arms, and the assisted demo begins extended and bends upward with support.

Valid ready/movement stages use a green wireframe, confirmed errors red, transient adjustments amber and unavailable tracking neutral. Visible joints are drawn even if another required joint is temporarily missing. The engine chooses the visible leg and, in single-leg exercises with both legs visible, switches to the leg that starts moving; that choice remains fixed during the repetition. Lying exercises can retry pose detection with the body oriented upright, then map coordinates back onto the original preview. The normal case still processes one frame at a time. The compact default view exposes stage, active limb, angle, target-held status and last completed score; expanded statistics remain available.

These are provisional software presets, not clinical prescriptions or proof of safe movement. Mini squat and squat use 2D projected knee angles and work best from the side; the other lower-body drivers use ML Kit's estimated 3D joint positions. The Android bridge normalizes x/z by image width and y by image height, so the lower-body adapter restores a common pixel scale before calculating 3D angles. ML Kit's estimated depth is not equivalent to the original MediaPipe landmarks, so the original numerical targets still need phone calibration. Elbow joint angles use estimated x/y/z positions to avoid a forearm pointing toward the camera collapsing to a degenerate 2D angle. Shoulder rotation uses a relative forearm x/z orientation proxy; it cannot measure clinical axial shoulder rotation reliably. ML Kit's in-frame likelihood is not a reliable test of whether an occluded limb is truly visible. Occlusion, unusual anatomy, support devices, and camera orientation can affect results. The patient should use the range prescribed by their clinician and stop for pain or bleeding. No diagnostic or clinical accuracy claim is made for the descriptive movement score.

The rule engines reject frames with missing or degenerate required joints, reset partial movements after a long tracking gap, and count only a completed outward and return cycle. A valid starting position must be stable for 0.3 seconds. Targets need a 0.2-second continuous hold, with a documented 2° margin for pose jitter. Both arms must meet their individual target in bilateral exercises; an average cannot hide one incomplete arm. Returning must reach the start range and the patient's own starting angle, then hold for 0.2 seconds. A 0.3-second posture-error confirmation ignores brief noise. After movement starts, a confirmed error stays incorrect for that repetition even if posture is later corrected. A stalled partial return is flagged; a cycle shorter than one second is not counted as correct. Lower-body angle smoothing and clinical calibration remain future work.

Assisted elbow flexion alternates left and right after an accepted supported repetition; an incorrect repetition retries the same side. Ordinary elbow flexion uses both arms together, with the upper arms beside the torso, matching the previous tutorial. One camera frame is processed at a time; excess frames are dropped. For an incorrect repetition, the app stores at most one local JPEG review frame from the first sustained error or the completed repetition. Feedback includes a specific error code and the movement stage where the first error occurred. Tapping the live feedback opens the full text and target instructions.

Upper-body scores follow the former shoulder assessment's structure: 45% form, 35% target-range completion, and 20% pace. Lower-body scores adapt the original source rule heuristic: a clean held repetition scores `min(100, 92 + ROM/10)`; a repetition with confirmed errors scores `max(40, 75 - 15 * distinct error categories)`. Counting a repeated cue once avoids penalizing the same mistake twice. Smoothness is displayed separately because pose noise can affect it. History stores target status, thresholds, feedback and available movement metrics. These scores describe observed movement and are not model probabilities. The live screen labels the lower-body result as a camera estimate.

## Review evidence and remaining validation

- All 133 Flutter regression tests passed, including 15 direct tests of the six source-derived lower-body adapters. Static analysis found no issues in the 11 changed Flutter files. Whole-project analysis still reports existing issues in the inactive `lib_current_backup` directory.
- Tests cover the source thresholds, six clean synthetic lower-body cycles, insufficient range, excessive mini-squat depth, loss of tracking and an obscured knee, in addition to the existing ten-exercise and UI suite. These tests verify state transitions and data shape; they do not establish accuracy on patients.
- A prior short CPH2691 practice run reported 60 processed pose frames averaging 29 ms each at a 66 ms dispatch interval, before this lower-body adapter. The new adapter still needs fresh real-device movement and performance checks; the earlier run does not verify it.
- Each exercise still needs filmed validation with varied participants, cameras, lighting, viewpoints, and range limitations before clinical use. Check false rep counts and missed reps as well as smoothness. Clinicians should review and approve exercise thresholds and feedback wording.

Android release builds need `android/app/proguard-rules.pro`: WorkManager's Room 2.2 generated database is created by reflection, so its constructor must survive R8 shrinking. Without this rule, the release APK crashes before `MainActivity` starts.
