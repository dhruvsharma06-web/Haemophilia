# On-device exercise assessment

The `codex/lower-body-source-integration` branch assesses live exercise camera frames on Android. The camera provides YUV frames to `LocalPoseBridge`, which uses MediaPipe world-coordinate tracking for ordinary elbow flexion/extension and the bundled ML Kit pose detector for all other exercises. Both paths provide image-space joints for the wireframe. The upper-body `ExerciseRulesAssessment` and lower-body source-rules adapter check joint angles, movement stages, posture, return to the start, and repetition timing. The Flutter screen draws the wireframe and feedback. Normal live frames are not uploaded to the Python backend. An assigned session saves completed repetition data and selected error review images to the existing Firebase history; an unassigned practice session does not save history.

This uses a pretrained general pose detector for joint locations. The six lower-body configurations and form checks come from `codex/lower-body-integration`. That branch's three Random Forest bundles are present in this repository as research artifacts; its own code never lets their predictions determine rep form or score. The model card reports one participant, zero cross-validation F1 for the mini-squat and seated-extension labels, and leakage affecting a straight-leg-raise label. The phone does not run those classifiers. Other app features may still use Firebase or the backend.

## Current tracking presets

The app displays these values before and during an exercise. `Start` and `target` are observed camera angles, in degrees. `ROM` is the minimum excursion for an accepted repetition. A repetition also requires a return to the starting range, stable tracking, and no sustained posture error.

| Exercise | Start | Target | Minimum ROM | Return to own start | Camera view |
| --- | ---: | ---: | ---: | ---: | --- |
| Assisted shoulder flexion | both shoulders ≤40° | both shoulders ≥150° | 75° | within 10° | Front |
| Shoulder rotation | within 8° of observed start | both forearms move ≥20° | 15° | within 4° | Front |
| Assisted elbow flexion | active elbow ≥150° | active elbow ≤90° | 50° | within 8° | Front |
| Elbow flexion and extension | left ≥152.59°, right ≥153.62° | left ≤70.76°, right ≤91.97° | left 87.93°, right 70.02° | left within 7.76°, right within 8.54° | Front oblique |
| Heel slide | knee ≥170° | knee ≤90° | 15° | within 10° | Side |
| Mini squat | knee ≥165° | knee ≤130° | 15° | within 8° | Side |
| Seated knee extension | knee ≤95° | knee ≥160° | 15° | within 10° | Side |
| Straight leg raise | hip ≥172° | hip ≤140° | 15° | within 10° | Side |
| Terminal knee extension | knee ≤145° | knee ≥170° | 15° | within 6° | Side |
| Squat | knee ≥155° | knee ≤120° | 15° | within 10° | Side |

The upper-body rules are `OnDeviceRules_v3`; lower-body targets and checks are adapted from the original branch. The source squat entry threshold of 105° occurs after its 120° target, so the app uses a 145° entry threshold and retains the 155° return and 120° target. See [exercise references and angle conversion](exercise-rule-references.md) for NHS/WFH sources and the distinction between sourced exercise goals and software scoring tolerances. Tutorials show the animation first and a small angle summary below it. The ordinary elbow demo is a forward curl with fixed upper arms, and the assisted demo begins extended and bends upward with support.

Valid ready/movement stages use a green wireframe, confirmed errors red, transient adjustments amber and unavailable tracking neutral. Visible joints are drawn even if another required joint is temporarily missing. The engine chooses the visible leg and, in single-leg exercises with both legs visible, switches to the leg that starts moving; that choice remains fixed during the repetition. Lying exercises can retry pose detection with the body oriented upright, then map coordinates back onto the original preview. The normal case still processes one frame at a time. The compact default view exposes stage, active limb, angle, target-held status and last completed score; expanded statistics remain available.

These are provisional software presets, not clinical prescriptions or proof of safe movement. Mini squat and squat use 2D projected knee angles and work best from the side; the other lower-body drivers use ML Kit's estimated 3D joint positions. The Android bridge normalizes x/z by image width and y by image height, so the lower-body adapter restores a common pixel scale before calculating 3D angles. ML Kit's estimated depth is not equivalent to the original MediaPipe landmarks, so the original numerical targets still need phone calibration. Assisted elbow joint angles use ML Kit estimated x/y/z positions to avoid a forearm pointing toward the camera collapsing to a degenerate 2D angle. Shoulder rotation uses a relative forearm x/z orientation proxy; it cannot measure clinical axial shoulder rotation reliably. ML Kit's in-frame likelihood is not a reliable test of whether an occluded limb is truly visible. Occlusion, unusual anatomy, support devices, and camera orientation can affect results. The patient should use the range prescribed by their clinician and stop for pain or bleeding. No diagnostic or clinical accuracy claim is made for the descriptive movement score.

The rule engines reject frames with missing or degenerate required joints, reset partial movements after a long tracking gap, and count only a completed outward and return cycle. A valid starting position must be stable for 0.3 seconds. Targets need a 0.2-second continuous hold. Legacy rules allow a 2° margin for pose jitter; the supplied elbow world-coordinate thresholds already include their engineering allowances and receive no clinical or jitter margin. The elbow engine does compare against a 0.05° numerical tolerance, because the causal low-pass filter approaches its input asymptotically and a patient holding exactly at a displayed threshold would otherwise settle a few thousandths of a degree short and be rejected; that tolerance is far below pose noise and is not a clinical allowance. Both arms must meet their individual target in bilateral exercises; an average cannot hide one incomplete arm. Returning must reach the start range and the patient's own starting angle, then hold for 0.2 seconds. A 0.3-second posture-error confirmation ignores brief noise. After movement starts, a confirmed error stays incorrect for that repetition even if posture is later corrected. A stalled partial return is flagged; a cycle shorter than one second is not counted as correct. Lower-body angle smoothing and clinical calibration remain future work.

Assisted elbow flexion alternates left and right after an accepted supported repetition; an incorrect repetition retries the same side. Ordinary elbow flexion uses both arms together, with the upper arms beside the torso, matching the previous tutorial. One camera frame is processed at a time; excess frames are dropped. For an incorrect repetition, the app stores at most one local JPEG review frame from the first sustained error or the completed repetition. Feedback includes a specific error code and the movement stage where the first error occurred. Tapping the live feedback opens the full text and target instructions.

Upper-body scores follow the former shoulder assessment's structure: 45% form, 35% target-range completion, and 20% pace. Lower-body scores adapt the original source rule heuristic: a clean held repetition scores `min(100, 92 + ROM/10)`; a repetition with confirmed errors scores `max(40, 75 - 15 * distinct error categories)`. Counting a repeated cue once avoids penalizing the same mistake twice. Smoothness is displayed separately because pose noise can affect it. History stores target status, thresholds, feedback and available movement metrics. These scores describe observed movement and are not model probabilities. The live screen labels the lower-body result as a camera estimate.

## Elbow world-coordinate candidate reference (October 21, 2026)

Ordinary elbow flexion/extension now routes through `ElbowWorldAssessment` rather than the shared ML Kit elbow rules. It consumes MediaPipe world landmarks in metres for 3D shoulder-elbow-wrist angles, and separately retains normalized image landmarks for drawing. Missing or incompatible world coordinates stop assessment rather than fall back to image or ML Kit angles. Other exercises, especially assisted shoulder flexion with bar, keep their existing tracking paths.

`LocalPoseService.initialize` sends `worldPose: true` only for the exercises converted to world coordinates (currently elbow flexion/extension and shoulder rotation), and the Android bridge then uses MediaPipe Tasks (`com.google.mediapipe:tasks-vision`) with the bundled `android/app/src/main/assets/pose_landmarker_lite.task` instead of the ML Kit detector. Both models are created lazily, so every other exercise still pays for ML Kit only. The bridge returns `world_landmarks` and `angle_source: pose_world_landmarks` alongside the image landmarks the wireframe uses. World coordinates are passed through unchanged: `cameraCoordinates` undoes a rotation about the normalized image centre, which is meaningless at metre scale, and the shoulder-elbow-wrist angle is invariant under a rigid rotation of the three landmarks anyway. Left and right come from the MediaPipe landmark indices (11/13/15 and 12/14/16), not from their screen positions. If the landmarker cannot be created, `initialize` reports `WORLD_POSE_UNAVAILABLE` and the engine holds at "Waiting" rather than silently measuring image-plane angles.

The exact supplied values and provenance are retained in `calibration/elbow-flexion-extension.json`. The source files were `mediapipe_angle_thresholds.json`, `angle_statistics.csv`, and `reviewed_rep_measurements.csv` (22 approved repetitions from a single source session). Raw reviewed CSV data is not bundled into the application. The source is labelled `person_specific_candidate`, not a universal clinical target or clinically validated classifier. Activating it in this development build does not establish suitability for other patients.

Each arm must independently meet its extension, held flexion, ROM and return-error limits. The supplied maximum bilateral angle difference is 34.758123896484435° and maximum ROM difference is 31.302325022900295°. Smoothing is causal and timestamp-based with a 0.08-second time constant. Counts, live wireframe status, feedback and saved arm metrics originate from this same assessment result. An incomplete stable return attempt is recorded as incorrect once, then requires a new stable start before another repetition.

Matching coordinate conventions is necessary but does not prove that Android MediaPipe Tasks and the source MediaPipe Pose 0.10.11/model produce identical measurements. The supplied metadata does not identify the original model variant. Validate on the phone against labelled recordings, including left/right identification, mirroring, occlusion, performance and threshold-boundary cases before relying on the classifications. No installed-phone or clinical accuracy validation is implied by passing synthetic tests.

## Shoulder rotation (October 21, 2026)

Shoulder rotation now routes through `ShoulderRotationAssessment`, following the supplied *Shoulder Rotation Measurement and Threshold Report* (15 October 2026). Unlike the elbow file, that report is a draft engineering specification rather than measurements from approved repetitions: only the elbow bend range (60–120°, target 90°) and the 12° sideways torso lean are carried over from the previous implementation. Every other limit — upper-arm position 20°, forward lean change 10°, torso twist 10°, wand level 10°, and the whole rotation sequence — is a **proposed engineering starting setting**, not a learned LSTM threshold and not a clinically validated limit. The constants and their provenance are in `calibration/shoulder-rotation.json`.

The report explicitly warns that the old counting values 8, 10, 3, 15 and 20 were normalized displacement units, not degrees, and must not be converted. The repository's unused 15° minimum excursion and 25° left/right ROM difference constants are likewise not adopted.

Rotation is measured as each forearm's signed azimuth in a torso-relative body frame built from world landmarks (up axis from hip midpoint to shoulder midpoint, lateral axis from the projected shoulder line, forward axis from their cross product), unwrapped across the ±180° boundary and smoothed with the same causal 0.08 s filter as the elbow engine. Both hands use the same body-frame axis, so moving the wand to one side gives both the same sign; the tests assert this directly. This is a forearm-orientation proxy, not direct anatomical shoulder rotation.

A repetition is centre → extreme → centre → opposite extreme, either side first, with a ±5° centre band and a 20° extreme held for 0.15 s. Neutral calibration needs a stable 0.5 s hold with acceptable starting posture. Posture violations are tracked per cycle and flag the repetition only when they cover at least 20% of valid samples; the observed fractions are still recorded for tuning. A tracking gap discards the incomplete cycle and requires centre again, and occlusion is never recorded as incorrect form. Duration and speed are reported but, per the report, do not pass or fail a repetition. The front-view 2D checks (sideways lean, wand level) use aspect-corrected image pixels; the 3D angles use world metres, and the two are never mixed.

The same device-validation caveat as the elbow applies, and it matters more here: the report asks for review of representative recordings covering both directions, varied camera distance, body proportions, reduced range, incorrect posture and occlusion before enabling these rules for patients. Single-camera depth estimates can make forearm rotation noisy.

## Review evidence and remaining validation

- All 133 Flutter regression tests passed, including 15 direct tests of the six source-derived lower-body adapters. Static analysis found no issues in the 11 changed Flutter files. Whole-project analysis still reports existing issues in the inactive `lib_current_backup` directory.
- Tests cover the source thresholds, six clean synthetic lower-body cycles, insufficient range, excessive mini-squat depth, loss of tracking and an obscured knee, in addition to the existing ten-exercise and UI suite. These tests verify state transitions and data shape; they do not establish accuracy on patients.
- A prior short CPH2691 practice run reported 60 processed pose frames averaging 29 ms each at a 66 ms dispatch interval, before this lower-body adapter. The new adapter still needs fresh real-device movement and performance checks; the earlier run does not verify it.
- Each exercise still needs filmed validation with varied participants, cameras, lighting, viewpoints, and range limitations before clinical use. Check false rep counts and missed reps as well as smoothness. Clinicians should review and approve exercise thresholds and feedback wording.

Android release builds need `android/app/proguard-rules.pro`: WorkManager's Room 2.2 generated database is created by reflection, so its constructor must survive R8 shrinking. Without this rule, the release APK crashes before `MainActivity` starts.
